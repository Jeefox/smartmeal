# SmartMeal

**v0.1.0-prototype.1** — первая зафиксированная версия рабочего прототипа. [Изменения версии](CHANGELOG.md).

Учебный планировщик питания и покупок: Java 21, Spring Boot 4.1.1, PostgreSQL и React + TypeScript + Vite.

## Что работает

- Регистрация и вход: хеширование паролей, серверная сессия и CSRF-защита.
- Личный профиль, анкета и предварительная оценка калорий; белок и клетчатка, сохранённая кухонная техника; подтверждение целей отдельно от расчёта.
- Продукты и категории; поиск и пагинация; создание и чтение рецептов с КБЖУ.
- Подбор меню на период для одного человека или семьи: индивидуальные нормы, доступная техника, гарниры, бюджет и ограничение разнообразия покупок.
- Меню дня: дробные порции, неизменяемые снимки рецептов, итоговое КБЖУ, редактирование черновика и подтверждение.
- Список покупок за 1–31 день: агрегация ингредиентов из снимков меню текущего пользователя.
- Сети и магазины, семь выбранных точек Тулы.
- Товары в упаковках, ручное добавление наблюдений цен и получение последнего наблюдения по дате.
- Flyway V1–V34, unit-тесты, интеграционные тесты PostgreSQL и проверки API с Spring Security.

Расчёты питания приблизительные, коэффициенты являются начальной моделью приложения. Предварительная рекомендация не заменяет сохранённую цель без подтверждения пользователя.
Подбор на период и расчёт закупки с бюджетом реализованы через API. Цены импортируются из каталогов и отмечаются как ориентиры, если применимость к выбранной сети/точке не подтверждена. Домашние запасы учитываются при подборе и расчёте покупок. Загрузка чеков остаётся будущей функцией; планирование партий готовых блюд, их приготовление, остатки и исправление ошибочных отметок уже доступны. Демонстрационные цены интерфейса не являются реальными предложениями магазинов.

## Домашние запасы

В React-клиенте откройте «Домашние запасы» (`/pantry`) в режиме API. Можно внести начальную партию, подтвердить фактическую покупку, исправить остаток или срок годности. Количества — граммы сырого покупаемого продукта без внешней упаковки: бананы с кожурой, макароны сухие. Начальные запасы пустые; приложение не предполагает, что соль или масло уже есть дома.

Предпросмотр и сохранение черновика не меняют наличие. Подтверждение меню резервирует доступные партии, прежде всего с ближайшим известным сроком. «Приготовил» в карточке блюда списывает сырьё один раз; можно пропустить блюдо или отменить ошибочное списание. Отмена дня освобождает оставшиеся резервы и сохраняет историю. Восстановление в черновик доступно только без истории движений ингредиентов этого дня.

Сначала из потребности вычитаются допустимые запасы, затем рассчитываются магазинные упаковки. Уже купленные продукты не увеличивают бюджет новых покупок; неизвестная историческая себестоимость не становится нулевой. Изменение запасов требует обновить оценку серверного предпросмотра перед сохранением.

Все команды учёта используют сессионную авторизацию, CSRF, `Idempotency-Key` и ревизию запасов; повтор одного запроса не создаёт второй покупки или списания. Журнал доступен через `GET /api/me/pantry/operations`. Часовой пояс учёта по умолчанию `Europe/Moscow`, настройка `smartmeal.pantry.time-zone`.

Партии с истёкшим указанным сроком видны, но не используются при подборе. Неуказанный срок помечается явно. Неотмеченное приготовление прошлых дней не списывает продукты автоматически: требуется сверка остатка. Сроки будущих покупок неизвестны; график закупок скоропортящихся продуктов и хранение готовых порций ещё не моделируются.

## Запуск бэкенда

Нужны JDK 21, Docker и Docker Compose.

Скопируйте `.env.example` в `.env` и задайте собственный `POSTGRES_PASSWORD`.
Spring Boot и Compose читают `.env` из корня проекта; в IDE выберите этот рабочий каталог.

```bash
docker compose up -d --wait
bash mvnw spring-boot:run
```

Бэкенд: http://localhost:8080. PostgreSQL: localhost:5433, база и пользователь `smartmeal`.
Локальное S3-хранилище SeaweedFS: http://localhost:9000. Обложки рецептов хранятся
в bucket `smartmeal-recipes`; PostgreSQL содержит только ключи и метаданные изображений.
Backend использует стандартный S3-совместимый API, поэтому production-хранилище задаётся через
`S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и `S3_BUCKET` без изменения доменного кода.
Пароль хранится только в локальном `.env`. Изменение этого файла не меняет пароль существующей БД.
Схемой управляет Flyway; применённые миграции не редактируются.

API требует входа. Для регистрации и входа сначала получите `GET /api/auth/csrf`, сохраните cookie и передайте токен в заголовке, имя которого указано в ответе.
Регистрация: `POST /api/auth/register` с JSON `{email, password}`. Вход: `POST /api/auth/login` с `application/x-www-form-urlencoded`, поля `email` и `password`.
После входа получите CSRF-токен заново. Текущий выход использует стандартный `POST /logout` с CSRF.

## Запуск фронтенда

Нужны Node.js >=22.12.0 и npm.

```bash
cd frontend
npm ci
npm run dev
```

Клиент: http://127.0.0.1:4173. Vite проксирует API в бэкенд на порту 8080.
В интерфейсе явно разделены деморежим и режим API. Демо хранится отдельно и не подменяет ошибки реального сервера.
Новый React-клиент находится в `frontend/`; `src/main/resources/static/` содержит прежний прототип, который не является production-сборкой React.

Подробности: [frontend/README.md](frontend/README.md), [документация интерфейса](docs/FRONTEND.md).

## Подбор меню на период

В режиме API откройте `/menu-generation` или кнопку «Подобрать неделю» в меню.
Поддерживается 1–14 дней, общий необязательный бюджет, выбор 1–6 сетей и покупка в одной
либо максимум двух сетях. Второй магазин предлагается при заданной минимальной экономии
или когда он улучшает покрытие корзины. Цена и наличие на полке не гарантируются.

Алгоритм учитывает тип приёма пищи, время, оборудование, известные аллергены и исключения,
подтверждённую историю за 21 день, ограничения повторов и целые упаковки на весь период.
По умолчанию один рецепт появляется максимум два раза с двумя полными днями между повторами.
Порции рецептов изначально целые: допустимое масштабирование и группу похожих блюд можно
настроить в карточке рецепта → «Настройки подбора». Проверенные сведения об аллергенах отмечаются
отдельно в каталоге продуктов с указанием основания проверки; неизвестные данные не считаются безопасными.

Генерация не обращается к внешним сайтам. Источники цен обновляются существующими сборщиками.
Свежесть наблюдений MANUAL и RECEIPT настраивается отдельно:
`smartmeal.planning.manual-price-max-age` (по умолчанию `P7D`) и
`smartmeal.planning.receipt-price-max-age` (`P14D`); каталоги используют собственный `expires_at`.
Промо-цены без модели условий не включаются автоматически.

Калории каждого дня сравниваются с текущей целью с техническим допуском ±10%.
Неполные цены дают `PARTIAL` и не превращаются в нулевые стоимости.
Оценочные цены помечены `COMPLETE_ESTIMATED`, полное покрытие наблюдениями — `COMPLETE_OBSERVED`.
`WITHIN/OVER/UNKNOWN/NOT_SET` относится к бюджету, отдельно от качества цены и успешности поиска.
При ограничении поиска сервер явно возвращает `LIMIT_REACHED`; найденная сумма не объявляется глобальным минимумом.

Основные ручки (серверная сессия и CSRF для записи):
- `POST /api/me/meal-plan-generations`: `from`, `to`, `budgetRub`, `allowedChainIds`, `city`,
  `purchaseMode` (`SINGLE_CHAIN`/`TWO_CHAINS`), `maxPreparationTimeByMeal`, `maxRecipeOccurrences`,
  `minRepeatGapDays`, `allowEstimatedPrices`, `minSplitSavingRub`, `seed`.
- `GET /api/me/meal-plan-generations/{id}`: собственный предпросмотр, сохраняющийся после перезагрузки страницы.
- `GET .../{id}/entries/{entryId}/alternatives`: до пяти замен с изменением всей корзины.
- `PUT .../{id}/entries/{entryId}`: `expectedRevision`, `recipeId`, `portions`.
- `PATCH .../{id}/entries/{entryId}/lock`: `expectedRevision`, `locked`.
- `POST .../{id}/regenerate`: `expectedRevision`, новый вариант с сохранением закреплений.
- `POST .../{id}/refresh`: `expectedRevision`, переоценка цен без изменения выбранной еды.
- `POST .../{id}/commit`: `expectedRevision`, `acceptWarnings` и заголовок `Idempotency-Key: <UUID>`.

Предпросмотр действует два часа. Сохранение атомарно создаёт черновики всех дней, не перезаписывая
уже существующие даты. Повтор с тем же ключом возвращает тот же результат; изменения рецептов,
ограничений, суточной цели и оценки покупок требуют перепроверки. Подтверждение черновиков
по-прежнему выполняется существующим API меню. Аллергии, исключённые продукты и доступное оборудование настраиваются на `/planning-preferences` через `GET/PUT /api/me/planning-preferences`; справочники доступны через `GET /api/planning-restrictions`. Типы приёмов пищи и необходимое оборудование рецепта задаются вместе с порциями на `/recipes/{id}/planning`. Допуски и цены не являются медицинскими или ценовыми гарантиями.

Проверки нового сценария:
```bash
bash mvnw -Dtest=PurchaseBasketCalculatorTest,PeriodMenuSelectorTest,PeriodPlanningIntegrationTest test
cd frontend
npm test
npm run test:e2e -- period-planning.e2e.ts
```


### Семейное меню

В разделе «Семья и порции» можно добавить до девяти человек помимо своего профиля.
Для каждого задаются имя, суточная цель калорий, аллергии и исключённые продукты.
Норма дополнительного человека пока вводится вручную. При подборе отметьте нужных людей:
блюда общие и подходят всем, порции делятся пропорционально индивидуальным целям,
бюджет и список покупок считаются на всех. Ваш профиль включён всегда.
Оборудование и домашние запасы общие, из аккаунта владельца.
Состав семьи и нормы фиксируются при сохранении меню и не меняются задним числом.

### Изолированное окружение тестов

Интеграционные тесты используют отдельные PostgreSQL и S3, без рабочих томов:

```bash
docker compose -f compose.test.yaml up -d --wait
bash mvnw -DargLine=-Xmx768m test
```

По умолчанию тестовая БД — `smartmeal_test` на порту `55439`, S3 — на `59001`.
Параметры можно переопределить через `-Dspring.datasource.*` и `-Dsmartmeal.storage.*`.
Перед созданием подключения тесты проверяют имя БД: допускаются имена с компонентом
`test`, например `smartmeal_test` или `smartmeal_test_ci`. Рабочая `smartmeal` запрещена.
Не запускайте интеграционные тесты на рабочей базе из IDE.
Контейнеры тестового окружения можно остановить командой
`docker compose -f compose.test.yaml down --volumes` — это отдельный проект `smartmeal-tests`.

### Покупки и пополнение запасов

В режиме API раздел «Покупки» открывает серверные списки (`/shopping-lists`).
После сохранения меню нажмите «Открыть покупки по меню»: повторное открытие
возвращает тот же список. Исходный расчёт остаётся доступен отдельно.
Галочка означает «собрано в корзину» и сама по себе не меняет домашние запасы.

Отметьте приобретённые продукты и нажмите «Добавить покупку в запасы».
В одном окне можно проверить фактическую массу, дату покупки, необязательные
сроки годности и суммы за строки. Если куплено меньше необходимого, остаток
сохраняется в списке. Цена из каталога не подставляется как фактически уплаченная.
Расходы сохраняются отдельно и автоматически не становятся наблюдениями цен магазинов.

API текущего аккаунта:

- `POST /api/me/shopping-sessions` — `{ "generationId": "..." }`; возвращает созданный или существующий список (200).
- `GET /api/me/shopping-sessions?status=OPEN&page=0` — списки по 20, статусы `OPEN`, `COMPLETED`, `ALL`.
- `GET /api/me/shopping-sessions/{id}` — состояние списка, ревизии, количества и расходы.
- `PATCH /api/me/shopping-sessions/{id}/items/{itemId}` — `expectedRevision`, `picked`, `skipped`.
- `POST /api/me/shopping-sessions/{id}/purchases` — `expectedRevision`, `expectedPantryRevision`, `items`.

Все команды записи требуют CSRF и UUID `Idempotency-Key`. Строка покупки содержит
`itemId`, `quantityG`, `receivedOn`, необязательные `expiresOn`, `actualTotalRub`
(сумма за всю строку) и `storeProductId` (проверяется соответствие базовому продукту).
Покупка и складские движения выполняются одной транзакцией. Повтор ключа с тем же
запросом возвращает прежний результат, изменение запроса под тем же ключом — 409.

При потере ответа клиент читает состояние перед явным повтором исходного запроса.
Неподтверждённая команда и форма хранятся раздельно по аккаунту и списку; успешный
выход очищает черновики этого аккаунта. Без сети можно сохранить одну ожидающую
отметку; прежде чем продолжать, её нужно отправить или отменить. Покупки без сети
не подтверждаются. Полная фоновая синхронизация нескольких офлайн-изменений в этот
сценарий не входит. Старые локальные галочки остаются в исходном расчёте и не
считаются складскими поступлениями.

Прямые ссылки `/shopping?from=...&to=...` и `/shopping?view=calendar` сохраняют
отдельный расчёт потребности по датам. Несколько серверных списков не объединяются
автоматически; пересекающиеся активные периоды показывают предупреждение.

Проверка: `bash mvnw -Dtest=ShoppingSessionIntegrationTest test` на тестовой БД и
`npx playwright test e2e/shopping-sessions.e2e.ts` в папке frontend.


## Составные приёмы пищи и индивидуальные количества

После применения V27 и V28 новый подбор по умолчанию использует `balancedMeals=true`.
Вместо увеличения одного рецепта генератор может выбрать основное блюдо, гарнир
и овощной компонент. Для каждого участника подбираются отдельные количества в
границах профиля рецепта и общей массы приёма пищи. Поиск учитывает калории,
заданные ориентиры белка и клетчатки, повторы и оценку покупок. Малый бюджет не
уменьшает индивидуальную цель калорий; при невозможности уложиться показывается
предупреждение. Оптимальность найденной цены не гарантируется.

В интерфейсе показывается примерный вес готовой еды каждого человека. Покупки и
списание запасов рассчитываются из исходных съедобных ингредиентов всех компонентов.
Составной приём пищи сохраняется одним неизменяемым снимком с вложенными рецептами,
поэтому подтверждение, покупки и приготовление остаются атомарными. Компоненты можно
заменять и закреплять отдельно. Старые подборы и сохранённые меню не пересчитываются:
для новых правил используйте «Новый подбор с гарнирами».

На `/nutrition-settings` можно явно задать индивидуальные ориентиры. Справочный
расчёт для подтверждённого взрослого предлагает белок 0,83 г/кг и клетчатку 25 г;
он требует отдельного сохранения и не изменяет цель калорий. Это ориентиры для
планирования, а не гарантия сытости. После приготовления доступна оценка количества
«мало / достаточно / много»; она сама не меняет настройки питания.

API (запись требует авторизации и CSRF):

- `GET/PUT /api/recipes/{id}/portion-profile` — роль, выход и границы готового количества.
- `GET/PUT /api/products/{id}/fiber` — клетчатка и происхождение данных.
- `GET /api/me/nutrition-targets`, `POST /api/me/nutrition-targets/suggest`,
  `PUT /api/me/nutrition-targets/{participantId}` — индивидуальные настройки.
- `GET /api/me/meal-plan-entries/{id}/portion-feedback`,
  `PUT /api/me/meal-plan-entries/{id}/portion-feedback/{participantId}` — обратная связь.

V28 добавляет восемь рецептов-компонентов и профили части существующих блюд.
Выход этих блюд отмечен как **приблизительный**, не измеренный. Для остальных
рецептов выход нужно заполнить перед участием в новом подборе. Значения клетчатки
добавлены для 15 сопоставленных продуктов из
[CoFID 2021](https://www.gov.uk/government/publications/composition-of-foods-integrated-dataset-cofid)
с сохранением кодов и описаний источника (атрибуция: Public Health England,
Open Government Licence v3.0). Отсутствующие значения не считаются нулём:
интерфейс показывает неполноту расчёта. Источники ориентиров:
[EFSA, белок](https://efsa.onlinelibrary.wiley.com/doi/10.2903/j.efsa.2022.7259),
[European Commission, клетчатка](https://knowledge-for-policy.ec.europa.eu/health-promotion-knowledge-gateway/dietary-fibre-recommendations-2_en).

Проверки: `BalancedPlanningIntegrationTest`, `CompositeMealsTest` на изолированной
тестовой БД; `frontend/e2e/balanced-meals.e2e.ts` проверяет интерфейс на фикстурах API.


### Короткая закупка и разнообразие

Для нового подбора интерфейс задаёт `maxShoppingProducts=10`; можно выбрать 7–10
разных продуктов **на весь выбранный период**. Для старых документов отсутствующее
поле сохраняет прежнее поведение без предела. API допускает явный целочисленный
предел 1–50; `null` отключает его. Предел не масштабируется на число членов семьи.

Считаются разные базовые продукты с положительным остатком к покупке после
распределения запасов по датам и срокам годности, включая товары без цены.
Несколько блюд с гречкой используют суммарную потребность и целые общие упаковки;
количество упаковок не увеличивает число позиций. Масло и специи тоже считаются,
если их необходимо купить. Покупать лишнюю крупу только ради большой упаковки
генератор не заставляет: выбирает доступные предложения для общей потребности.

Генератор предпочитает сочетания с общими ингредиентами; блюда по-прежнему должны
соблюдать ограничения продуктов, оборудования, времени и индивидуального количества.
История учитывает все компоненты подтверждённых меню за предыдущие 21 день и
приготовленные компоненты отменённых меню. Частые повторы основных блюд получают
более сильный штраф, чем гарниры; история остаётся предпочтением, чтобы единственное
безопасное блюдо не блокировало меню. Гарантии отсутствия повторов при малом каталоге нет.

Если поиск не заполнил период, интерфейс показывает известные препятствия:
отсутствие рецептов по типу приёма пищи, время, фильтры безопасности/оборудования,
незаполненный выход, недостаток основных рецептов при правилах повторов и ограничение
закупки. Сообщение об ограниченном поиске не утверждает математическую невозможность.
Превышение заданного предела нельзя сохранить даже с согласием на предупреждения.
Изменение запасов требует нового расчёта. Старые сохранённые меню не переписываются.

Проверки: `GroceryPolicyTest`, `BalancedPlanningIntegrationTest` (общие упаковки,
недельный предел, несовместимые ограничения, история гарниров), браузерные сценарии
`balanced-meals.e2e.ts` и `period-planning.e2e.ts`.

## Готовка на несколько дней

После миграции V29 откройте `/cooking` («Готовка и остатки» в меню).
Сохранённые черновики можно явно подтвердить одной командой на весь период.
Затем одинаковые компоненты разных приёмов пищи объединяются в общую партию:
например, курица на два ужина с разными гарнирами или рис на несколько дней.
Сопоставление выполняется по неизменяемому снимку рецепта, а не только названию.
Меню и индивидуальные нормы при этом не меняются.

1. Выберите компоненты, дату приготовления и явно укажите дату хранения. По
   умолчанию отмечены ближайшие два дня; это не рекомендация срока хранения.
2. До подтверждения готовки продукты только резервируются, на дату приготовления
   всей партии. Список покупок за этот день включает ингредиенты для будущих порций.
3. После приготовления укажите фактический выход и нажмите «Приготовил партию».
   Сырые продукты списываются целиком один раз; фактический выход меняет учёт
   готовой массы, но не переписывает калорийность сохранённых снимков.
4. Приготовьте оставшиеся компоненты приёма пищи в обычном меню. Уже готовые
   компоненты повторного списания не требуют. После еды отдельная отметка
   «Съедено» уменьшает остаток готовой партии. Это не полный дневник фактического
   питания с частично съеденными порциями.
5. Пропущенная порция освобождает готовый остаток. Его можно переназначить на
   совместимый рецепт до указанной даты хранения. Списание готового остатка
   не возвращает сырые продукты; будущая потребность пересчитывается.

Дата хранения задаётся пользователем для конкретного блюда и условий; приложение
не выводит её из рецепта автоматически. Истёкшую партию нельзя использовать или
отметить съеденной. Отмена запланированной партии не тратит продукты. Отмена дня,
пропуск, возврат обычного списания и история приготовленных партий согласованы;
после отметки «Съедено» возврат сырых ингредиентов запрещён.

Учёт готовой еды применяется к явно созданным общим партиям. Генератор меню не
создаёт их молча. Имеющиеся списки покупок, привязанные к сохранённому подбору,
остаются историческими списками; актуальная потребность по датам доступна через
календарный расчёт покупок. Частичное съедание/списание и автоматический подбор
новых рецептов из свободного готового остатка в этот этап не входят.

API `/api/me/cooking-batches`:

- `GET ?from=...&to=...` — свободные компоненты, партии, распределение и черновики.
- `POST /confirm-period` — `expectedRevision`, `from`, `to`; подтверждение периода.
- `POST` — `expectedRevision`, `cookOn`, `useBy`, `entries` (`entryId`, `componentId`).
- `POST /{id}/prepare` — `expectedRevision`, `actualYieldG`.
- `POST /{id}/assign` — `expectedRevision`, `entries`; использование свободного остатка.
- `POST /{id}/discard` — `expectedRevision`; отмена плана / списание остатка.
- `POST /entries/{entryId}/consume` — `expectedRevision`; приём пищи съеден.

Все команды записи требуют CSRF и UUID `Idempotency-Key`, используют общую
ревизию запасов и транзакционную блокировку владельца. Повтор того же ключа
возвращает прежний результат; другой запрос под этим ключом даёт конфликт.
Недостаток сырья, чужие записи и повторное распределение одного компонента
не создают частичных списаний. Браузер после потери ответа сначала перечитывает
состояние и не выполняет повторное приготовление автоматически.

Проверки: `CookingIntegrationTest`, `PantryIntegrationTest`, `ShoppingListServiceTest`,
`frontend/e2e/cooking.e2e.ts` и `frontend/src/cooking.test.ts`.

### Главный экран дня

В режиме API главная страница объединяет меню, индивидуальные количества готовой
еды и действия приготовления. Для составных блюд количества каждого участника
видны сразу, подробные рецепты и расчёты раскрываются отдельно. Рядом с блюдом
отмечаются готовые компоненты, а совместимый свободный остаток можно использовать
без перехода в складской раздел. После приготовления остальных компонентов
употребление партии отмечается кнопкой «Съедено» на той же карточке.

Готовка с запасом выключена по умолчанию. Переключатель на главной включает
предложения общих партий на ближайшие два или три дня. В дополнительных настройках
можно выбрать удобные дни недели; предложение не переходит через следующий
выбранный день готовки. Меню не меняется автоматически, партии не создаются и
продукты не списываются от включения переключателя. Для каждой партии нужны явное
подтверждение, дата хранения и последующее подтверждение фактического выхода.
Выключение режима не отменяет уже запланированные партии.

Эти необязательные настройки хранятся в текущем браузере отдельно по аккаунтам;
сами меню, партии, остатки и операции остаются на сервере. Полный учёт доступен в
`/cooking`, операции запасов и редкие действия дня — в свёрнутых блоках. Недоступность
данных готовой еды показывается явно; она не трактуется как отсутствие остатков.

Проверки интерфейса: `frontend/e2e/today.e2e.ts`; правила предложений и сохранение
настроек: `frontend/src/today-cooking.test.ts`. Новых миграций для этого экрана нет.


### Исправление ошибочных отметок готовки

В «Других действиях» блюда и карточке партии можно исправить фактический вес всей приготовленной партии или отменить ошибочное «съедено». Вес порций, включая уже съеденные, пересчитывается пропорционально; состав рецепта, калории, сырые запасы и сроки хранения сохраняются.

Отмена «съедено» возвращает готовую еду в остатки: для подтверждённого дня она остаётся назначенной этому блюду, для отменённого — освобождается. Истёкший срок хранения не продлевается; для списанных партий автоматический возврат запрещён. История содержит причину, время и значения до/после с привязкой к операции. Повтор команды с тем же Idempotency-Key не дублирует исправление.

Миграция V30 добавляет историю. API:

- POST `/api/me/cooking-batches/{id}/weight-corrections`: `expectedRevision`, `actualYieldG`, `reason`.
- POST `/api/me/cooking-batches/entries/{id}/consumption-reversal`: `expectedRevision`, `reason`.
- GET `/api/me/cooking-batches/{id}/corrections`: последние 50 исправлений.

Запись требует CSRF и заголовок `Idempotency-Key`. Проверки: CookingIntegrationTest, cooking-corrections.test.ts, today.e2e.ts.


### Замена блюда без пересборки периода

В карточке блюда предпросмотра доступны три группы: «Из тех же продуктов», «Дешевле» и «Быстрее». Каждая группа содержит до трёх разных блюд из найденных допустимых кандидатов; это ограниченный поиск, а не доказанный глобальный минимум. Составные блюда сохраняют закреплённые компоненты и индивидуальные количества. Ограничения продуктов, оборудования, времени, повторов и количества покупок сохраняются; замена не ухудшает уже достигнутый допуск калорий и известные целевые дефициты белка/клетчатки участников.

Сравнивается вся корзина периода после округления упаковок и учёта пригодных доступных запасов. «Из тех же продуктов» означает отсутствие новых позиций для покупки, а не неизменное количество упаковок. «Дешевле» требует известных полных оценок обеих корзин и строго меньшей стоимости; при неизвестных ценах экономия не заявляется. «Быстрее» требует меньшего указанного времени приготовления.

GET существующего endpoint `.../entries/{entryId}/alternatives` возвращает дополнительно `goals`, `impact` (новые/исключённые продукты, количество позиций, время, порции участников, исходная стоимость и момент расчёта) и `comparisonKey`. PUT замены передаёт этот ключ вместе с `expectedRevision`. Если цены или запасы изменились, сервер отвечает 409 `REPLACEMENT_COMPARISON_CHANGED`; интерфейс предлагает обновить расчёт и заново проверить вариант. Форматы 1 и 1.00 не создают ложный конфликт. Запись перепроверяет версию запасов под блокировкой владельца.

Выбор варианта открывает сравнение и не записывает изменения до отдельного подтверждения. Другие приёмы пищи остаются прежними. Механизм работает в предпросмотре до сохранения: сохранённые/подтверждённые меню и выполненные приготовления через него не перезаписываются. Миграция БД не требуется.


### Замена в сохранённом меню и отмена

На экране дня и в календаре недели у сохранённого блюда доступна «Заменить блюдо». Можно менять будущие/сегодняшние записи в черновике или подтверждённом дне, если состояние ингредиентов OPEN и нет активной/съеденной связи с общей партией. Прошедшие, отменённые, приготовленные и пропущенные записи защищены. Запланированную общую партию сначала нужно отменить явно; приготовленные остатки не освобождаются автоматически. Для перекусов автозамена пока не предлагается.

Предпросмотр использует текущие ограничения и цены, сохранённые нормы участников, настройки исходного подбора и неизменные снимки остальных блюд. Для вручную созданного дня без исходного подбора используются неделя выбранной даты, Тула и до шести доступных сетей. Сравниваются оставшиеся покупки с учётом запасов и готовых компонентов; уже оплаченные расходы не выдаются за будущую стоимость. Бюджет исходного подбора не считается оставшимся бюджетом.

POST проверяет версию запасов и отпечаток актуальных меню/цен/ограничений, меняет одну запись и перестраивает резервы под блокировкой владельца. Сырые остатки не списываются и не возвращаются. Идемпотентный повтор не создаёт вторую замену. Аудит V32 сохраняет снимки, количества и корзины до/после. Можно отменить последнюю действующую замену: только если приготовление не началось, запись не была вручную изменена и старый рецепт всё ещё допустим. История оплат и купленные продукты сохраняются.

Сохранённые списки покупок пересчитываются автоматически: сохраняются ID оплаченных строк и их покупки, добавляются новые продукты, ненужные позиции имеют нулевой остаток. Отметки «взял»/«пропустил» сбрасываются только при изменении требуемого количества. Меняется revision списка, поэтому покупка со старого экрана требует повторной проверки. Список, впервые открытый по старому подбору после замены, также загружает актуальные потребности. Исходный документ подбора остаётся историческим снимком; действующее меню видно на экране дня/недели.

API под `/api/me/meal-plan-entries/{entry}/replacements`:

- GET `/status` — допустимость и последняя отменяемая замена.
- GET — варианты и revision запасов.
- POST — `expectedRevision`, `recipeId`, `portions`, `candidateKey`, `comparisonKey`.
- POST `/{change}/undo` — `expectedRevision`.

Записи требуют CSRF и `Idempotency-Key`. Миграция V32 добавляет аудит и маркер пересчёта списков.


### Безопасность и доступ к каталогу

Обычный аккаунт управляет только своими меню, семьёй, запасами и покупками. Запись в общий
каталог продуктов, рецептов, аллергенов и прямое редактирование общих цен доступны редактору.
В `.env` задайте `SMARTMEAL_CATALOGUE_EDITOR_IDS=UUID-существующего-аккаунта`
(несколько UUID — через запятую), перезапустите backend и войдите заново.
ID аккаунта можно посмотреть в ответе `/api/me/profile` (`userId`). Email без подтверждения не служит основанием для выдачи прав; регистрация не позволяет задать свой UUID.
Frontend получает только флаг `canEditCatalogue`, сервер проверяет роль независимо от интерфейса.

Регистрация возвращает одинаковый пустой `204` для нового и уже занятого адреса.
Для существующего аккаунта пароль не заменяется. Пароль содержит минимум 8 символов и
не более 72 байт UTF-8 — ограничение bcrypt; длинные пароли не обрезаются.

Выход и истечение сессии очищают личные браузерные черновики. Вкладки синхронизируют смену
сессии без передачи профилей/токенов. Открытые формы сбрасываются при смене пользователя;
незавершённые запросы старой сессии отменяются.

Встроенные лимиты для одного backend: 20 запросов входа/регистрации в минуту на IP и 20 попыток входа на аккаунт,
120 изменяющих запросов в минуту на IP и аккаунт, 10 загрузок обложки в минуту на IP.
Подбор выполняется максимум в двух запросах одновременно и одном на аккаунт; превышение —
`429` с `Retry-After`. Значения общих лимитов настраиваются через
`smartmeal.security.auth-requests-per-minute` / `smartmeal.security.writes-per-minute`.
Для нескольких экземпляров необходим общий лимитер на reverse proxy/Redis.

Для сервера используйте профиль `prod` (`--spring.profiles.active=prod`), отдельные случайные
`POSTGRES_PASSWORD` (не менее 16 символов) и `S3_SECRET_KEY` (не менее 32 символов), а также
`S3_ACCESS_KEY`. Приложение не запустится с публичным development-ключом S3.
Backend слушает `127.0.0.1`; наружу публикуется только HTTPS reverse proxy.
Пример `frontend/nginx.example.conf` включается в HTTPS server block после настройки TLS.
Он перезаписывает forwarded-заголовки; в `prod` доверие ограничено loopback-прокси.
Cookie сессии имеет HttpOnly/SameSite=Lax, в prod также Secure; время неактивности — 30 минут.
Development-значения хранилища предназначены только для локального запуска.
Не открывайте порты PostgreSQL/S3/backend напрямую. TLS-сертификаты, права S3 и резервных
копий на реальном сервере проверяются отдельно при развёртывании.

Регрессионные проверки безопасности: `SecurityRegressionTest`, `RequestProtectionFilterTest`,
`RecipeImageProcessorTest`, `frontend/e2e/security.e2e.ts` и `frontend/src/session-boundary.test.ts`.


### Моя кухня

При первой настройке выбирается доступная техника. Даже пустой выбор сохраняется на сервере;
после этого вопрос не повторяется. Изменить технику можно в **Профиль → Моя кухня → Изменить**.
Пункт «Плита» объединяет сковороду и кастрюлю, остальные приборы выбираются отдельно.
Новый подбор учитывает сохранённые приборы, а уже сохранённые меню не переписываются.

Миграция V33 добавляет аэрогриль и постоянную отметку завершённой настройки. V34 размечает технику ранних рецептов без изменения их инструкций. Для аккаунтов
с ранее выбранным оборудованием шаг считается пройденным. API: `GET/PUT /api/me/kitchen`;
выбор меняет только технику владельца сессии, не затрагивая аллергии и исключённые продукты.
`equipmentConfigured` в профиле отличает первый запуск от осознанного выбора без техники.
Новый каталог блюд и команды импорта описаны в `data/recipes/README.md`.
