# SmartMeal

Учебный планировщик питания и покупок: Java 21, Spring Boot 4.1.1, PostgreSQL и React + TypeScript + Vite.

## Что работает

- Регистрация и вход: хеширование паролей, серверная сессия и CSRF-защита.
- Личный профиль, анкета и предварительная оценка калорий; подтверждение цели отдельно от расчёта.
- Продукты и категории; поиск и пагинация; создание и чтение рецептов с КБЖУ.
- Меню дня: дробные порции, неизменяемые снимки рецептов, итоговое КБЖУ, редактирование черновика и подтверждение.
- Список покупок за 1–31 день: агрегация ингредиентов из снимков меню текущего пользователя.
- Сети и магазины, семь выбранных точек Тулы.
- Товары в упаковках, ручное добавление наблюдений цен и получение последнего наблюдения по дате.
- Flyway V1–V23, unit-тесты, интеграционные тесты PostgreSQL и проверки API с Spring Security.

Расчёты питания приблизительные, коэффициенты являются начальной моделью приложения. Предварительная рекомендация не заменяет сохранённую цель без подтверждения пользователя.
Подбор на период и расчёт закупки с бюджетом реализованы через API. Цены импортируются из каталогов и отмечаются как ориентиры, если применимость к выбранной сети/точке не подтверждена. Домашние запасы учитываются при подборе и расчёте покупок. Загрузка чеков и партии готовых блюд остаются будущими функциями. Демонстрационные цены интерфейса не являются реальными предложениями магазинов.

## Домашние запасы

В React-клиенте откройте «Домашние запасы» (`/pantry`) в режиме API. Можно внести начальную партию, подтвердить фактическую покупку, исправить остаток или срок годности. Количества — граммы сырого покупаемого продукта без внешней упаковки: бананы с кожурой, макароны сухие. Начальные запасы пустые; приложение не предполагает, что соль или масло уже есть дома.

Предпросмотр и сохранение черновика не меняют наличие. Подтверждение меню резервирует доступные партии, прежде всего с ближайшим известным сроком. «Приготовил» в карточке блюда списывает сырьё один раз; можно пропустить блюдо или отменить ошибочное списание. Отмена дня освобождает оставшиеся резервы и сохраняет историю. Восстановление в черновик доступно только без истории движений ингредиентов этого дня.

Сначала из потребности вычитаются допустимые запасы, затем рассчитываются магазинные упаковки. Уже купленные продукты не увеличивают бюджет новых покупок; неизвестная историческая себестоимость не становится нулевой. Изменение запасов требует обновить оценку серверного предпросмотра перед сохранением.

Все команды учёта используют сессионную авторизацию, CSRF, `Idempotency-Key` и ревизию запасов; повтор одного запроса не создаёт второй покупки или списания. Журнал доступен через `GET /api/me/pantry/operations`. Часовой пояс учёта по умолчанию `Europe/Moscow`, настройка `smartmeal.pantry.time-zone`.

Партии с истёкшим указанным сроком видны, но не используются при подборе. Неуказанный срок помечается явно. Неотмеченное приготовление прошлых дней не списывает продукты автоматически: требуется сверка остатка. Сроки будущих покупок неизвестны; график закупок скоропортящихся продуктов и хранение готовых порций ещё не моделируются.

## Запуск бэкенда

Нужны JDK 21, Docker и Docker Compose.

Скопируйте `.env.example` в `.env` и задайте собственный `POSTGRES_PASSWORD`.
Spring Boot и Compose читают `.env` из корня проекта; в IDE выберите этот рабочий каталог.

```bash
docker compose up -d --wait
bash mvnw spring-boot:run
```

Бэкенд: http://localhost:8080. PostgreSQL: localhost:5433, база и пользователь `smartmeal`.
Локальное S3-хранилище SeaweedFS: http://localhost:9000. Обложки рецептов хранятся
в bucket `smartmeal-recipes`; PostgreSQL содержит только ключи и метаданные изображений.
Backend использует стандартный S3-совместимый API, поэтому production-хранилище задаётся через
`S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и `S3_BUCKET` без изменения доменного кода.
Пароль хранится только в локальном `.env`. Изменение этого файла не меняет пароль существующей БД.
Схемой управляет Flyway; применённые миграции не редактируются.

API требует входа. Для регистрации и входа сначала получите `GET /api/auth/csrf`, сохраните cookie и передайте токен в заголовке, имя которого указано в ответе.
Регистрация: `POST /api/auth/register` с JSON `{email, password}`. Вход: `POST /api/auth/login` с `application/x-www-form-urlencoded`, поля `email` и `password`.
После входа получите CSRF-токен заново. Текущий выход использует стандартный `POST /logout` с CSRF.

## Запуск фронтенда

Нужны Node.js >=22.12.0 и npm.

```bash
cd frontend
npm ci
npm run dev
```

Клиент: http://127.0.0.1:4173. Vite проксирует API в бэкенд на порту 8080.
В интерфейсе явно разделены деморежим и режим API. Демо хранится отдельно и не подменяет ошибки реального сервера.
Новый React-клиент находится в `frontend/`; `src/main/resources/static/` содержит прежний прототип, который не является production-сборкой React.

Подробности: [frontend/README.md](frontend/README.md), [документация интерфейса](docs/FRONTEND.md).

## Проверки

Все тесты бэкенда, включая интеграционные, требуют запущенную локальную PostgreSQL:

```bash
bash mvnw test
```

Только unit-тесты калькуляторов, без БД:

```bash
bash mvnw '-Dtest=*CalculatorTest' test
```

Из `frontend/`:

```bash
npm test
npm run build
npm run test:e2e
```

Для браузерных тестов нужен Chromium Playwright (`npx playwright install chromium`). Они используют изолированные ответы API; интеграционные Java-тесты обращаются к PostgreSQL и откатывают свои записи.

## Локальные файлы

## Подбор меню на период

В режиме API откройте `/menu-generation` или кнопку «Подобрать неделю» в меню.
Поддерживается 1–14 дней, общий необязательный бюджет, выбор 1–6 сетей и покупка в одной
либо максимум двух сетях. Второй магазин предлагается при заданной минимальной экономии
или когда он улучшает покрытие корзины. Цена и наличие на полке не гарантируются.

Алгоритм учитывает тип приёма пищи, время, оборудование, известные аллергены и исключения,
подтверждённую историю за 21 день, ограничения повторов и целые упаковки на весь период.
По умолчанию один рецепт появляется максимум два раза с двумя полными днями между повторами.
Порции рецептов изначально целые: допустимое масштабирование и группу похожих блюд можно
настроить в карточке рецепта → «Настройки подбора». Проверенные сведения об аллергенах отмечаются
отдельно в каталоге продуктов с указанием основания проверки; неизвестные данные не считаются безопасными.

Генерация не обращается к внешним сайтам. Источники цен обновляются существующими сборщиками.
Свежесть наблюдений MANUAL и RECEIPT настраивается отдельно:
`smartmeal.planning.manual-price-max-age` (по умолчанию `P7D`) и
`smartmeal.planning.receipt-price-max-age` (`P14D`); каталоги используют собственный `expires_at`.
Промо-цены без модели условий не включаются автоматически.

Калории каждого дня сравниваются с текущей целью с техническим допуском ±10%.
Неполные цены дают `PARTIAL` и не превращаются в нулевые стоимости.
Оценочные цены помечены `COMPLETE_ESTIMATED`, полное покрытие наблюдениями — `COMPLETE_OBSERVED`.
`WITHIN/OVER/UNKNOWN/NOT_SET` относится к бюджету, отдельно от качества цены и успешности поиска.
При ограничении поиска сервер явно возвращает `LIMIT_REACHED`; найденная сумма не объявляется глобальным минимумом.

Основные ручки (серверная сессия и CSRF для записи):
- `POST /api/me/meal-plan-generations`: `from`, `to`, `budgetRub`, `allowedChainIds`, `city`,
  `purchaseMode` (`SINGLE_CHAIN`/`TWO_CHAINS`), `maxPreparationTimeByMeal`, `maxRecipeOccurrences`,
  `minRepeatGapDays`, `allowEstimatedPrices`, `minSplitSavingRub`, `seed`.
- `GET /api/me/meal-plan-generations/{id}`: собственный предпросмотр, сохраняющийся после перезагрузки страницы.
- `GET .../{id}/entries/{entryId}/alternatives`: до пяти замен с изменением всей корзины.
- `PUT .../{id}/entries/{entryId}`: `expectedRevision`, `recipeId`, `portions`.
- `PATCH .../{id}/entries/{entryId}/lock`: `expectedRevision`, `locked`.
- `POST .../{id}/regenerate`: `expectedRevision`, новый вариант с сохранением закреплений.
- `POST .../{id}/refresh`: `expectedRevision`, переоценка цен без изменения выбранной еды.
- `POST .../{id}/commit`: `expectedRevision`, `acceptWarnings` и заголовок `Idempotency-Key: <UUID>`.

Предпросмотр действует два часа. Сохранение атомарно создаёт черновики всех дней, не перезаписывая
уже существующие даты. Повтор с тем же ключом возвращает тот же результат; изменения рецептов,
ограничений, суточной цели и оценки покупок требуют перепроверки. Подтверждение черновиков
по-прежнему выполняется существующим API меню. Аллергии, исключённые продукты и доступное оборудование настраиваются на `/planning-preferences` через `GET/PUT /api/me/planning-preferences`; справочники доступны через `GET /api/planning-restrictions`. Типы приёмов пищи и необходимое оборудование рецепта задаются вместе с порциями на `/recipes/{id}/planning`. Допуски и цены не являются медицинскими или ценовыми гарантиями.

Проверки нового сценария:
```bash
bash mvnw -Dtest=PurchaseBasketCalculatorTest,PeriodMenuSelectorTest,PeriodPlanningIntegrationTest test
cd frontend
npm test
npm run test:e2e -- period-planning.e2e.ts
```


### Семейное меню

В разделе «Семья и порции» можно добавить до девяти человек помимо своего профиля.
Для каждого задаются имя, суточная цель калорий, аллергии и исключённые продукты.
Норма дополнительного человека пока вводится вручную. При подборе отметьте нужных людей:
блюда общие и подходят всем, порции делятся пропорционально индивидуальным целям,
бюджет и список покупок считаются на всех. Ваш профиль включён всегда.
Оборудование и домашние запасы общие, из аккаунта владельца.
Состав семьи и нормы фиксируются при сохранении меню и не меняются задним числом.

### Изолированное окружение тестов

Интеграционные тесты используют отдельные PostgreSQL и S3, без рабочих томов:

```bash
docker compose -f compose.test.yaml up -d --wait
bash mvnw -DargLine=-Xmx768m test
```

По умолчанию тестовая БД — `smartmeal_test` на порту `55439`, S3 — на `59001`.
Параметры можно переопределить через `-Dspring.datasource.*` и `-Dsmartmeal.storage.*`.
Перед созданием подключения тесты проверяют имя БД: допускаются имена с компонентом
`test`, например `smartmeal_test` или `smartmeal_test_ci`. Рабочая `smartmeal` запрещена.
Не запускайте интеграционные тесты на рабочей базе из IDE.
Контейнеры тестового окружения можно остановить командой
`docker compose -f compose.test.yaml down --volumes` — это отдельный проект `smartmeal-tests`.
