# Предпросмотр меню одного дня

POST `/api/me/meal-plans/preview` с cookie-сессией и CSRF:

```json
{
  "planDate": "2033-02-01",
  "breakfastMaxPreparationTimeMin": 15,
  "lunchMaxPreparationTimeMin": 45,
  "dinnerMaxPreparationTimeMin": 45
}
```

planDate обязателен. Лимиты — целые >= 0; если отсутствуют или null, используются 15/45/45 минут.
Используется текущий положительный dailyCalorieTarget из профиля. Нет цели — 409.
Предпросмотр не создаёт, не обновляет и не подтверждает меню, в том числе когда на дату уже есть меню.

## Ответ

200: `{planDate,dailyCalorieTarget,nutritionTotal,calorieDeviation,withinTargetTolerance,entries,warnings}`.

- nutritionTotal: calories/protein/fat/carbs всего дня, до 2 знаков HALF_UP;
- calorieDeviation: калории минус цель (положительное — избыток);
- withinTargetTolerance: отклонение не больше 10% от цели;
- entries: три строки BREAKFAST, LUNCH, DINNER;
- строка: `{mealType,recipeId,recipeName,portions,preparationTimeMin,nutrition,lastPlannedDate,recipeFingerprint}`;
- lastPlannedDate: последняя дата этого рецепта в своих предыдущих 21 днях либо null.

portion — количество стандартных порций рецепта (не масса), от 0.5 до 2 с шагом 0.25.
Пищевая ценность считается из текущих ингредиентов и их съедобной массы, без увеличения калорий из-за очистки.
Суммы до округления рассчитываются через общий знаменатель servings, как и для сохранённого меню.
Сумма округлённых строк может отличаться от округлённого итога на сотую.

Коды warnings:

- TARGET_NOT_REACHED — доступные выбранные варианты не дали отклонение <=10%; результат всё равно показан;
- RECENT_RECIPES_USED — использован хотя бы один рецепт из своей истории 21 дня;
- CATALOGUE_SEARCH_LIMIT — подходящих рецептов больше 500 для приёма, поиск ограничен.

400 — неверное тело/дата/отрицательное время, 401 — нет сессии с корректным CSRF,
403 — отсутствует/неверен CSRF, 409 — нет цели или не удалось собрать три разных подходящих рецепта.
На нехватку кандидатов ограничения не ослабляются, неполный день не возвращается как успешный.

## Подбор

Сначала фильтруются рецепты по mealTypes и общему времени готовки. Нужен хотя бы один ингредиент.
Учитываются сохранённые user_excluded_products, user_allergies через product_allergens и требуемое
recipe_equipment через user_equipment. Отсутствующая разметка аллергенов/оборудования сама по себе
не означает их отсутствие в действительности; API проверки этих справочников — отдельная работа.
Нулевая суммарная калорийность исключается из кандидатов генератора.

Целевые доли: 25%/40%/35%. Это начальные настройки алгоритма приложения, не индивидуальная
медицинская рекомендация. Оценка: ошибка дневной калорийности с весом 10 + сумма ошибок приёмов
+ 0.02 × отклонение порций от 1 + штрафы истории.
За каждое вхождение в истории штраф 0.20 × (22 - возраст в днях) / 21.
Учитываются черновики и подтверждённые планы пользователя за [planDate-21;planDate-1].
Это история планирования, а не подтверждение фактически съеденной еды.
Один и тот же recipeId запрещён в двух приёмах текущего дня. Различные похожие рецепты ещё не группируются.
Повторы в истории — мягкое предпочтение, не строгий запрет 21 дня; их наличие видно в warnings.

Поиск детерминированный и ограниченный: максимум 500 рецептов на приём в порядке ID;
по индивидуальной оценке остаются 40 рецептов, на каждом шаге — 100 лучших частичных вариантов.
Это эвристический поиск, без гарантии глобального оптимума и без разнообразия при повторном запросе
с неизменными данными. Дефицит найденных комбинаций может требовать расширения каталога/лимитов,
даже если более широкий перебор мог бы найти вариант.

Не учитываются бюджет, цены и заготовки; нет недельной генерации или замены похожих групп блюд.
Сохранение выбранного предпросмотра реализовано ниже; интеграция frontend — следующий этап.
Новая миграция для предпросмотра не нужна: используется разметка V11 и существующие таблицы ограничений.

## Сохранение выбранного дня

POST `/api/me/meal-plans/preview/save`, сессия и CSRF обязательны:

```json
{
  "options": {
    "planDate": "2033-02-01",
    "breakfastMaxPreparationTimeMin": 15,
    "lunchMaxPreparationTimeMin": 45,
    "dinnerMaxPreparationTimeMin": 45
  },
  "dailyCalorieTarget": 2000,
  "entries": [
    {"mealType":"BREAKFAST","recipeId":"UUID из preview","portions":1,"recipeFingerprint":"64 символа из preview"},
    {"mealType":"LUNCH","recipeId":"UUID из preview","portions":1,"recipeFingerprint":"64 символа из preview"},
    {"mealType":"DINNER","recipeId":"UUID из preview","portions":1,"recipeFingerprint":"64 символа из preview"}
  ]
}
```

UUID и fingerprint в примере — текстовые заглушки: копируйте настоящие поля из ответа preview.
Строки предпросмотра теперь содержат recipeFingerprint — SHA-256 канонического снимка рецепта.
Масштаб BigDecimal (1 против 1.000000) отпечаток не меняет. Он проверяет актуальность состава,
инструкции, параметров и пищевой ценности, а не является токеном авторизации или серверным preview ID.
Сервер не хранит предпросмотр и не доверяет переданным клиентом калориям/инструкциям/снимкам.

Нужны ровно три строки — BREAKFAST/LUNCH/DINNER, разные recipeId.
Порции 0.5..2 с шагом 0.25, до двух знаков после запятой. Порядок входных строк не важен.
options повторяют параметры генерации; dailyCalorieTarget — цель из ответа preview.
Клиент может изменить порции в допустимых пределах; сохранение не гарантирует прежнее отклонение
по калориям после такого изменения. Проверить окончательный итог можно в ответе сохранения.

Ответ 201 — обычный MealPlanResponse, Location `/api/me/meal-plans?date=YYYY-MM-DD`.
Создаётся DRAFT, три записи со снимками и position=1 в каждом приёме; подтверждение отдельно.
Профиль и его цель не изменяются. Сохраняются выбранные блюда, повторного запуска генератора нет.
После сохранения работают существующие просмотр, редактирование порций, подтверждение и список покупок.

Проверяются текущая цель профиля, принадлежность рецепта приёму пищи, лимит времени, наличие состава,
положительная калорийность, сохранённые аллергии, исключённые продукты и требуемое оборудование.
Калории и снимки строятся на сервере общим RecipeSnapshotFactory, используемым и при ручном добавлении блюда.

- 400 — неверная форма/количество строк/типы/повторы/порции/fingerprint;
- 404 — выбранный рецепт не существует;
- 409 — на дату уже есть меню (даже пустое или подтверждённое), нет цели либо предпросмотр устарел;
- 401/403 — сессия/CSRF, как у остальных операций записи.

При изменившемся составе, информации для покупок, калорийной цели или ограничениях сервер не подменяет
выбор новым меню: отклоняет сохранение и предлагает обновить preview. Новое меню не создаётся частично.
Изменение цен и истории планирования не запускает повторную генерацию: этот этап не сохраняет бюджетный расчёт.

Сохранение транзакционное: при ошибке записи любого блюда новый день целиком откатывается.
Запросы создания меню сериализуются по пользователю (и обычный POST создания тоже); дополнительно
работает существующий UNIQUE(user_id,plan_date). Два одновременных сохранения на одну дату дают
один созданный день и один конфликт. Повтор после успеха возвращает 409, не дублирует и не перезаписывает день.
Миграция для сохранения не требуется.

## Подбор с бюджетом в одном магазине

Тот же `POST /api/me/meal-plans/preview` принимает два дополнительных поля, только вместе:

```json
{
  "planDate": "2033-02-01",
  "breakfastMaxPreparationTimeMin": 15,
  "lunchMaxPreparationTimeMin": 45,
  "dinnerMaxPreparationTimeMin": 45,
  "storeId": 11,
  "budget": 500.00
}
```

`storeId` положительный; `budget` больше нуля, до 10 целых и 2 дробных знаков. Валюта текущей версии — рубли. Без обоих полей поведение прежнее, `budgetEstimate` равен `null`. Одно поле без другого, отрицательные значения и лишние дробные знаки дают 400; неизвестный магазин — 404, неактивный — 409.

Ответ дополнен `budgetEstimate`:

- `budget` — заданный бюджет закупки;
- `status`: `WITHIN_BUDGET`, `OVER_BUDGET`, `UNKNOWN`;
- `excess` — `max(knownPurchaseCost - budget, 0)`; при неполных ценах это только известная часть превышения;
- `shoppingEstimate` — обычная структура сметы: `storeId`, `complete`, `knownPurchaseCost`, `items` с требуемым весом, выбранной упаковкой, количеством упаковок, ценой, стоимостью покупки, остатком и датой наблюдения цены. `from` и `to` равны дате меню. `containsDrafts=false`, поскольку предпросмотр ещё не является сохранённым меню.

Вес всех одинаковых продуктов сначала суммируется по трём блюдам с учётом порций, количества порций рецепта и доли съедобной части. Итог округляется до сотых грамма, как в обычном списке покупок. Упаковки приобретаются целиком, для продукта выбирается предложение с наименьшей стоимостью покупки. Это закупка с нулевыми домашними запасами, включая остатки, а не стоимость съеденной доли продуктов. Масса ингредиентов берётся до приготовления.

Правила цен совпадают с обычной сметой: активные товары выбранного магазина, последнее неаннулированное обычное наблюдение; акционные цены не используются. При отсутствии цены стоимость позиции — `null`; она не становится бесплатной. При неполной смете статус всегда `UNKNOWN`, даже если известная сумма меньше бюджета. Приложение не придумывает цены. Наблюдения пока не отбрасываются по возрасту: дата цены доступна в каждой строке.

Порядок выбора среди рассмотренных комбинаций: полная смета + бюджет + калорийность в пределах 10%; затем полная смета с калорийностью в пределах 10% и минимальным превышением; затем неполная смета в пределах 10%; затем варианты за пределами калорийности. В рамках успешного бюджета сохраняется оценка калорийности, распределения по приёмам пищи и разнообразия. Рецепты остаются разными, ограничения времени, исключения и оборудование сохраняются.

Поиск ограничен: до 500 рецептов на приём пищи, объединение до 40 лучших по питанию и 40 по стоимости, до 100 частичных комбинаций. Часть комбинаций сохраняется по стоимости для возможности общих упаковок. Это эвристика, не доказательство глобального оптимума или невозможности уложиться в бюджет. Предупреждение `BUDGET_SEARCH_LIMITED` сопровождает бюджетный подбор. Дополнительные предупреждения: `PRICES_INCOMPLETE` и `BUDGET_EXCEEDED`. Фронтенд должен показывать «Не удалось найти вариант в пределах бюджета», а не утверждать, что такого меню не существует.

Сохранение использует прежний `/preview/save`: в `options` передаются исходные параметры, включая `storeId` и `budget`. Сохраняются блюда и их снимки; бюджет, магазин и цены не фиксируются в меню, цены повторно не проверяются этим методом. Статус бюджета описывает только момент предпросмотра. Для актуальной закупки после сохранения следует запросить обычную смету. Нельзя показывать ранее рассчитанную стоимость как гарантированную цену на кассе.
