# Пригодность рецептов и кандидаты для меню

Первый этап автоматического подбора: классификация рецептов и отбор по времени.
Генерации меню, оптимизации калорий, истории повторов и бюджета здесь ещё нет.
Кандидаты не проверяются на аллергию, оборудование или персональные исключения —
эти ограничения должны быть добавлены перед полноценным генератором.

## Типы приёмов пищи

Рецепт имеет `mealTypes`: массив из `BREAKFAST`, `LUNCH`, `DINNER`, `SNACK`.
Один рецепт может подходить для нескольких приёмов. Порядок ответа — порядок enum,
повторяющиеся значения не создают дубликаты. GET карточки и списка рецептов возвращают это поле.

POST `/api/recipes` принимает необязательное поле `mealTypes`.
Без поля или при null создаётся неразмеченный рецепт с `mealTypes: []`.
Старый контракт создания сохраняется. Неизвестный enum или null внутри массива — 400.

PUT `/api/recipes/{id}/meal-types`, тело `{"mealTypes":["BREAKFAST","SNACK"]}`,
полностью заменяет разметку. Массив обязателен, может быть пустым для снятия разметки;
null и неизвестные значения отклоняются с 400. Возвращается RecipeSummaryResponse.
404 — рецепт отсутствует; нужны сессия и CSRF. Название рецепта не используется для угадывания типа.

Миграция V11 создаёт recipe_meal_types с составным PK и FK ON DELETE CASCADE.
Существующие рецепты остаются неразмеченными: они доступны в обычном каталоге,
но не участвуют в подборе, пока пользователь не задаст mealTypes.
Редактирование разметки не меняет уже сохранённые снимки меню.

## Поиск кандидатов

GET `/api/recipes/candidates?mealType=BREAKFAST&maxPreparationTimeMin=15&q=каша&page=0&size=20`

- mealType обязателен, одно значение enum;
- maxPreparationTimeMin обязателен, целое >= 0, верхняя граница включена;
- q необязателен, обычная подстрока названия без учёта регистра, пробелы по краям удаляются;
- page >= 0, по умолчанию 0; size 1..100, по умолчанию 20;
- порядок фиксирован: name ASC, id ASC.

Отбираются только рецепты с указанным типом, временем не выше предела и хотя бы одним ингредиентом.
Используется существующее общее preparationTimeMin: время активной работы и разогрева отдельно не моделируется.
Время 0 допускает продукты/блюда без готовки. Недостаток рецептов не ослабляет ограничения.

Ответ — RecipePageResponse: `{content,page,size,totalElements,totalPages}`.
Строка — `{id,name,description,preparationTimeMin,servings,mealTypes}`.
Пустая выдача — 200 с content: []; ошибки параметров — 400; без сессии — 401.
GET не сохраняет меню и не требует CSRF.

Сначала нужно разметить хотя бы несколько реальных рецептов для каждого приёма.
Результат этого API — допустимые по типу и времени кандидаты, а не готовый персональный рацион.

На следующем этапе добавлен [предпросмотр одного дня](MEAL_PLAN_PREVIEW_API.md):
это отдельный POST API с целью профиля, историей и персональными фильтрами.
Обычный GET кандидатов остаётся неперсональным поиском по типу и времени.
