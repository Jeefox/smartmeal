# Каталог товаров магазина

`GET /api/store-products?storeId=1&name=рис&productId=5&page=0&size=20`

Требуется cookie-сессия. CSRF для GET не нужен.

- `storeId` обязателен, положительный ID конкретной торговой точки.
- `name` необязателен: подстрока названия упаковки без учёта регистра, пробелы по краям удаляются. Пустая строка не ограничивает выдачу. `%` и `_` рассматриваются как обычные символы.
- `productId` необязателен: положительный ID базового продукта, фильтруется вместе с name через AND.
- `active`: необязательный boolean, по умолчанию true. false возвращает отключённые упаковки для просмотра и восстановления.
- `page`: от 0, по умолчанию 0.
- `size`: от 1 до 100, по умолчанию 20.

Сортировка фиксирована: name ASC, id ASC. По умолчанию возвращаются активные StoreProduct выбранного магазина; active=false выбирает неактивные. Расчёты закупки всегда используют только активные упаковки.
Формат: `{content:[StoreProductResponse],page,size,totalElements,totalPages}`.
Строка: `{id,storeId,productId,name,packageWeightG,active,createdAt,updatedAt}`.
Поля цены в этот ответ не входят.

Ошибочные параметры дают 400, без сессии — 401, неизвестный магазин — 404,
неактивный магазин — 409. Нет совпадений, неизвестный положительный productId
или страница за пределами выдачи — 200 с пустым content.

Для выбранного SKU доступны существующие методы:

- `GET /api/store-products/{id}` — карточка упаковки;
- `GET /api/store-products/{id}/prices/latest` — последняя цена (включая акционные), 404 если цена ещё не внесена;
- `POST /api/store-products/{id}/prices` — добавить ручное наблюдение цены с CSRF.

Не путать последнюю цену карточки с оценкой закупки: оценка использует последнюю НЕакционную цену.
Миграция для поиска не требуется: используются существующие таблицы и индексы.

## История цен

`GET /api/store-products/{id}/prices?page=0&size=20`

Ответ `{content:[PriceObservationResponse],page,size,totalElements,totalPages}`.
Наблюдение: `{id,storeProductId,price,observedAt,priceSource,promotional,createdAt}`.
Сортировка фиксирована: observedAt DESC, id DESC. Включены обычные и акционные цены;
история неактивных товаров и магазинов остаётся доступной. Дата наблюдения имеет приоритет
над датой внесения: добавленная сегодня старая цена не становится первой только из-за нового ID.

`page >= 0`, `size` от 1 до 100, по умолчанию 20; ID товара должен быть положительным.
Без наблюдений и за пределами последней страницы — 200 с пустым content.
Неизвестный товар — 404; неверные параметры — 400; без сессии — 401.
GET не требует CSRF. История не изменяет наблюдения и не меняет правила расчёта закупки.

## Аннулирование ошибочной цены

`POST /api/store-products/{storeProductId}/prices/{priceId}/invalidate`

Тело: `{"reason":"Ошибка при вводе суммы"}`. Причина обязательна, не пустая, до 300 символов.
Положительные ID, авторизованная сессия и CSRF обязательны. Ответ 200 — PriceObservationResponse.
404 — магазинный товар или принадлежащая ему запись цены не найдены; 400 — ошибка параметров;
401 — нет сессии (с корректным CSRF), 403 — отсутствует/неверен CSRF.
Можно аннулировать цену неактивного товара. Операция доступна авторизованным пользователям,
как и существующее внесение цен в общий каталог; индивидуальная принадлежность цен пока не вводится.

Ответы цен (POST, latest, history) дополнены `invalidated`, `invalidatedAt`, `invalidationReason`.
Дата — Instant, причина обрезается по краям. У действующей записи дата и причина null.
Пользователь аннулирования сохраняется из Authentication во внутреннем аудите `invalidated_by`,
но его email не публикуется в общем API цен.

Запись и её исходные цена/дата/акционность/источник остаются в истории. История включает аннулированные записи.
Повторный POST возвращает исходное аннулирование, не переписывая причину, дату и автора.
Изменение сериализуется блокировкой строки в транзакции. Восстановление и редактирование записи не предусмотрены:
правильную цену следует добавить отдельным новым наблюдением.

Latest пропускает аннулированные записи, включая акционные; если действующих нет — 404.
Оценка закупки и сравнение используют только НЕакционные НЕаннулированные наблюдения.
После аннулирования последней подходящей цены используется предыдущая подходящая; если её нет,
строка остаётся без известной стоимости. В интерфейсе после успешного POST нужно обновить историю,
последнюю цену и все оценки/сравнения, которые могли её использовать.

Миграция V10 добавляет поля аудита и частичный индекс действующих наблюдений; старые цены остаются действующими.

## Активность магазинного товара

`PUT /api/store-products/{id}/activity`, тело `{"active":false}` или `{"active":true}`.
Требуются сессия и CSRF. active обязателен, null отклоняется. Ответ 200 — StoreProductResponse
с актуальным updatedAt. Неизвестный ID — 404, неположительный ID/неверное тело — 400.
Повторное задание того же состояния не меняет updatedAt. Изменение сериализуется блокировкой строки.

Отключённый SKU исключается из каталога по умолчанию и из оценок/сравнения, но остаётся доступным
через GET /api/store-products/{id}, каталог с active=false и историю цен. Его цены не удаляются.
Восстановление SKU возвращает его в расчёты с прежними действующими наблюдениями; новую цену
оно не создаёт и не подтверждает её актуальность. Изменения действуют для последующих запросов;
уже открытые оценки после успешного PUT нужно обновить. Новых колонок для активности не требуется.

## Фильтры истории цен

`GET /api/store-products/{id}/prices?promotional=false&invalidated=false&page=0&size=20`

Оба фильтра необязательные, сочетаются через AND:

- promotional=true — акционные, false — обычные, без параметра — любые;
- invalidated=true — аннулированные, false — действующие, без параметра — любые.

Пагинация и totalElements относятся к отфильтрованной истории.
Порядок остаётся observedAt DESC, id DESC. Без фильтров сохраняется прежняя полная история.
Нераспознаваемое значение boolean — 400. Фильтры истории не изменяют latest и правила оценки закупки.
