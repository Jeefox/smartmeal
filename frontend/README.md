# SmartMeal · React frontend

React + TypeScript + Vite, React Router, TanStack Query, Lucide. Версии зафиксированы в package-lock.json. Java backend остаётся в корне репозитория.

## Разработка

Node.js >= 22.12.0, npm. Из папки frontend:

```bash
npm ci
npm run dev
```

Открыть http://127.0.0.1:4173/. Vite проксирует `/api` на `http://127.0.0.1:8080`. Если backend слушает другой адрес:

```bash
SMARTMEAL_API_URL=http://127.0.0.1:8081 npm run dev
```

Для открытия с телефона в своей локальной сети: `npm run dev -- --host 0.0.0.0`, затем адрес компьютера с портом 4173. Это разработческий сервер; не публикуйте его в интернет. Проверка на настоящем телефоне не выполнялась.

```bash
npm test
npm run build
npm run preview
npm run format
```

## Режимы

По умолчанию выбран явно подписанный **деморежим**. Переключатель «Источник данных» расположен внизу бокового меню; на телефоне меню открывается кнопкой слева вверху.

**Демо**: рецепты, ручное меню, профиль, цены и покупки — учебные данные. Персональные демоданные имеют отдельные ключи `smartmeal.v2.demo.*` в localStorage, не синхронизируются с сервером и не превращаются в production-данные. Не используйте демо как единственное хранилище реальных ограничений питания. Автоматический подбор не симулируется: действие объясняет отсутствие серверного планировщика.

**API**: продукты, категории, карточка и создание рецепта используют Spring Boot. Каталог ожидает краткий DTO со страницы сервера. Нет локального индекса UUID, подмены ошибки API демоданными или записи реальных профилей/меню в localStorage. Авторизация, анкета, расчёт калорий и сохранение цели подключены к серверу. Меню дня подключено к серверу. Потребность в продуктах по периоду подключена к серверу. Магазины, цены, упаковки и сохранение отметок покупок пока ждут своих контрактов.

## API

Используются текущие пути:

- `GET /api/products?q=&page=0&size=12&categoryId=`.
- `GET /api/product-categories`.
- `POST /api/recipes` с текущим CreateRecipeRequest.
- `GET /api/recipes/{id}` с текущим RecipeResponse.

Каталог подготовлен к `GET /api/recipes?q=&page=0&size=9&sort=createdAt,desc`:

```ts
type RecipePageResponse = {
  content: RecipeSummaryResponse[];
  page: number;
  size: number;
  totalElements: number;
  totalPages: number;
};
type RecipeSummaryResponse = {
  id: string;
  name: string;
  description: string | null;
  preparationTime: number;
  servings: number;
};
```

Клиент нормализует `preparationTime` из текущего краткого DTO в `preparationTimeMin`. Также поддерживается вариант с уже согласованным `preparationTimeMin`. Состав и инструкции запрашиваются только в карточке; КБЖУ в кратком DTO необязательны. Изображение без данных заменяется иллюстративной заглушкой. API не обязан возвращать полный RecipeResponse для каждой карточки.

Список в backend менялся параллельно реализации frontend; окончательная компиляция/работа этого метода с реальной БД не проверялась. Параметры сортировки соответствуют полям сущности; публичный whitelist должен задаваться backend. Фильтры времени/категории рецепта и ограничений в API-режиме не применяются, пока не появится контракт. Поиск q обрабатывается backend; frontend не обещает то, чего backend не реализовал.

`PUT /api/recipes/{id}` подготовлен в редакторе, но endpoint и правила владельца пока требуют backend. Ссылка на редактирование показывается для собственных деморецептов; серверная доступность действий должна основываться на правах пользователя после появления auth/owner.

Ошибки: ProblemDetail с `detail`, `title`, `errors[{field,message}]`; вложенные ошибки ингредиентов возвращают форму на нужный шаг. 409 объясняется конфликтом. Сохранение защищено от повторного нажатия. Регистрация и вход используют реальные запросы. Перед каждым изменяющим запросом получается актуальный CSRF, заголовок берётся из headerName. После успешного входа токен запрашивается заново. JWT/localStorage для сессии не используются; пароли не сохраняются.

## Меню, стоимость и покупки

Демо рассчитывает сумму по снимкам рецептов, допускает дробные порции и сохраняет закрепления. Редактирование рецепта не переписывает уже выбранный снимок. Изменение меню/параметров помечает список устаревшим; перестроение требует явного подтверждения и предупреждает о сбросе отметок. Подтверждение серверного меню не реализовано, статус меню — черновик.

Потребность продукта агрегируется на весь период перед округлением упаковок. Суммы demo хранятся в целых копейках; это иллюстрация, не перенос серверной бизнес-арифметики в JS. Отдельно показаны стоимость использованного количества, покупки упаковок и остатки. Неизвестная цена не равна нулю; показывается известная часть без фиктивного остатка бюджета. Режимы «по известным ценам» и «предварительная оценка» различаются. Риск превышения верхней границы не выдаётся за успех. Цены не являются реальными ценами магазинов, доступность товара не предполагается.

Замена — только демонстрация другой упаковки того же Product с явным подтверждением; при отмеченных аллергиях неизвестный состав блокирует замену. Автоматические рекомендации питания, гарантии безопасности и реальные источники цен отсутствуют.

## PWA и production

`npm run build` создаёт `dist/`. Отдавать его отдельным веб-сервером; `/api` проксировать в backend. Вложенные SPA-пути должны возвращать index.html. Пример Nginx-конфига — `nginx.example.conf`. Старый `src/main/resources/static/` сохранён и не заменяется автоматически: `localhost:8080` продолжает отдавать старый прототип, новый клиент в разработке — `localhost:4173`.

Service worker регистрируется **только в production-сборке**. Кешируется публичная оболочка и локальные иконки; API, авторизация и сторонние фотографии не кешируются. Ключ кеша зависит от хеша сборки; новая версия ждёт закрытия старых вкладок, не перезагружая несохранённые формы. Offline-чтение демосписка требует отдельного согласия; изменение статусов без сети блокируется. Реальный список покупок пока не подключён; выход очищает память запросов и потенциальные пользовательские кеши, оболочка PWA остаётся общей. Установка на Android/iOS и HTTPS-публикация ещё требуют отдельной проверки; manifest не означает одинаковую установку на всех ОС.

Шрифты — системные, без CDN. Демофотографии загружаются с Unsplash; при недоступности остаётся заглушка. Для production-каталога нужны собственные/лицензированные изображения и согласованный контракт URL.

## Подключение аккаунта и опроса · 18 октября 2026

Маршруты: `/register`, `/login`, `/welcome`, `/profile`, `/onboarding`. Экран входа/регистрации включает API-режим; остальные реальные экраны защищены серверной проверкой профиля. Можно включить API-режим через переключатель источника данных. Демо сохраняется отдельно и не заменяет неуспешные серверные запросы.

Регистрация отправляет только email/password и после 201 предлагает вход. Автоматического входа и вопроса о калориях при регистрации нет. Вход передаёт form-urlencoded, принимает 204, обновляет CSRF и загружает профиль. При null dailyCalorieTarget показывается предложение пройти опрос или перейти к каталогу. Незаполненная анкета не закрывает каталог.

Опрос: параметры тела → активность → цель → результат. Последовательно выполняются PUT анкеты и GET расчёта. Результат показывает основной обмен, поддержание и рекомендацию. Клиент не рассчитывает ни формулы, ни коэффициенты, ни поправки на цель. Отдельные действия «Принять рекомендацию» и «Подтвердить свою цель» вызывают PUT калорийности. Сохранение анкеты и GET расчёта сами по себе цель не меняют. Опрос можно открыть повторно; автоматический расчёт явно обозначен для взрослых вне беременности/грудного вскармливания и как предварительная оценка.

Подключённый контракт:

- `GET /api/auth/csrf` → token/headerName/parameterName; cookie остаётся в браузере.
- `POST /api/auth/register` → 201/409; JSON email/password.
- `POST /api/auth/login` → 204/401; URLSearchParams email/password.
- `GET /api/me/profile` → nullable поля профиля.
- `PUT /api/me/profile` → age/sex/heightCm/weightKg/activityLevel/goal, без dailyCalorieTarget.
- `GET /api/me/energy-estimate` → restingCalories/maintenanceCalories/recommendedCalories; 409 отображается без выдуманного результата.
- `PUT /api/me/profile/daily-calorie-target` → положительное целое dailyCalorieTarget.

401 переводит защищённый интерфейс ко входу и убирает данные аккаунта из памяти. Ошибка сети отличается от 401: не объявляет пользователя вышедшим и позволяет повторить запрос. 403 не вызывает автоматический повтор записи. Ошибки ProblemDetail показываются рядом с полями; пустые Security-ответы имеют понятные сообщения.

### Выход и proxy

Изучен SecurityConfig; на работающем backend проверен стандартный Spring Security **POST /logout**: CSRF принят, сервер ответил 302 на `/login?logout`. Это не выдуманный `/api/auth/logout`. Vite и пример Nginx проксируют точный `/logout` дополнительно к `/api`. Клиент не следует перенаправлению, затем проверяет GET профиля: успешным выходом считается только подтверждённый 401. Сбой сети не маскируется локальным «выходом».

Запросы используют credentials same-origin и cache no-store. API никогда не пишется в service worker Cache Storage. Реальные профиль, черновик анкеты, расчёт и cookie не попадают в localStorage. Смена аккаунта/выход очищает Query Cache; демоданные остаются отдельным учебным пространством.

## Серверное ручное меню · 18 октября 2026

В режиме API экраны `/` и `/week` используют серверные меню. Дата отображается в URL `?date=YYYY-MM-DD`, на неделе выбираются отдельные дни. Чтение пустого дня (404) не создаёт меню и не подставляет демоданные. Неделя делает GET по каждому дню; недельного автоподбора/общего подтверждения не симулируем.

Подключены:

- `GET /api/me/meal-plans?date=...` → MealPlanResponse или null только при 404; сетевые/прочие ошибки не равны пустому дню.
- `POST /api/me/meal-plans` с `{planDate}` по явному действию «Создать меню».
- `POST /api/me/meal-plans/{planId}/entries` с `{recipeId,mealType,portions}`.
- `PUT /api/me/meal-plans/{planId}/entries/{entryId}` с `{portions}`.
- `DELETE` записи →204 с подтверждением пользователя.
- `POST /api/me/meal-plans/{planId}/confirm` без тела, с предупреждением о неизменяемости.

`MealPlanResponse.entries` содержит `recipeSnapshot` и серверное `nutrition` выбранных порций. Карточка блюда открывает этот снимок; ссылка на текущий рецепт выделена отдельно. `nutritionTotal` дня берётся из ответа сервера, клиент не пересчитывает его по рецептам. Для DRAFT цель берётся из `dailyCalorieTarget` ответа, для CONFIRMED сервер возвращает снимок цели. Изменение профиля инвалидирует запросы меню; подтверждённые значения остаются зафиксированными.

Добавление доступно из дня и карточки рецепта. Если дня нет, действие «Создать меню и добавить» явно создаёт черновик. Повторное создание при 409 не воспроизводится: читаем уже созданный день. CONFIRMED запрещает добавление, порции, удаление и повторное подтверждение в UI; сервер остаётся окончательной проверкой. Нет цели или блюд — кнопка подтверждения отключена с пояснением. 409 конкурентного изменения показывается и вызывает только чтение, без повторного POST/PUT.

После успешной мутации заново загружается день. Если запись прошла, а последующее чтение не удалось, UI сообщает именно это и не предлагает автоматически повторять запись. Порции вводятся отдельно от сохранения: положительное число, до четырёх целых и двух дробных разрядов, согласно DTO. Все изменения проходят через общий CSRF/cookie-клиент.

Серверные меню, снимки и порции не сохраняются в localStorage, не смешиваются с демоменю и не получают локальные фиктивные замены/закрепления. Автоподбор по питанию и бюджету по-прежнему отсутствует.

## Живой список покупок · 18 октября 2026

`/shopping` в режиме API теперь открывает `src/pages/LiveShopping.tsx`. Старый демонстрационный экран сохранён в отдельном компоненте и не используется как fallback реальных данных.

Контракт: `GET /api/me/shopping-list?from=YYYY-MM-DD&to=YYYY-MM-DD`, ответ `{from,to,containsDrafts,items:[{productId,productName,quantityG}]}`. Диапазон 1–31 день включительно; обе даты обязательны, конец не раньше начала. Клиент проверяет формат и реальные календарные даты через UTC (без ошибок перехода часов). Итоговую проверку и агрегирование выполняет backend. Порядок, имена из снимков и количества ответа не пересчитываются/не объединяются повторно в JS; одинаковые названия с разными Product ID остаются отдельными строками.

Период хранится в URL; поля применяются кнопкой «Показать список», есть быстрый выбор дня/недели. Из меню ссылка передаёт соответствующий период. При containsDrafts показывается предупреждение о предварительности и необходимости обновления перед покупкой. Пустые items при200 — корректная пустая выдача. 400/404/500 и потеря сети не превращаются в пустой список. При неудачном обновлении ранее полученные данные помечены как потенциально устаревшие. 401 обрабатывается общим механизмом сессии. Запрос отменяется при смене ключа/периода, использует cookie и no-store.

После обновления меню инвалидируются запросы потребности. Строки списка и период принадлежат ключу текущего userId; реальные данные не сохраняются в localStorage/Cache Storage и не смешиваются с демо. Время на экране — локальное время получения ответа, а не выдуманное время изменения серверных данных. Live-список без сети доступен только пока данные остаются в памяти вкладки; после перезагрузки offline-данные не подставляются.

Цены, упаковки, домашние остатки, SKU, статусы «куплено»/«не найдено» и замены отсутствуют в текущем контракте и не симулируются в live-интерфейсе. Поэтому нет суммы в рублях, количества упаковок и фиктивных checkbox. Пользователь видит фактическую потребность в граммах.

Проверки: всего 66 unit-тестов и 21 браузерный сценарий, включая шесть новых сценариев списка. Проверены диапазоны 1/31/32 дня, границы месяца/года и високосный день, порядок/количества ответа, drafts, пустая выдача, ошибки400/сеть/401, сохранение периода в URL, отсутствие утечки в localStorage, длинные русские названия и ширины360/390/768/1440px. `npm run build` — TypeScript и production-сборка. Браузерные проверки используют изолированный API, не изменяют рабочую БД. Java, ветка dev и локальное ТЗ не изменяются, коммит и push не выполняются.

## Магазин и оценка покупок · 20 октября 2026

В API-режиме на `/shopping` сохранён просмотр потребности без выбора магазина. Над ним добавлен поиск по введённому городу и необязательной сети; адреса загружаются из `GET /api/stores?city=...&chainId=...`, сети — из `GET /api/retail-chains`. IDs берутся только из ответа. Выбор конкретной точки запускает `GET /api/me/shopping-estimate?from=...&to=...&storeId=...` для применённого периода 1–31 день. Изменения дат в полях применяются по кнопке. `/stores` ведёт к этому сценарию, не показывает фиктивные точки в API-режиме.

Показываются исходная потребность, выбранный SKU, вес и количество целых упаковок, цена упаковки, стоимость строки, остаток (целые граммы, округление вниз на сервере), дата наблюдения и источник цены. Все вычисления выполняет backend. Строки с `null` не считаются бесплатными. При `complete=false` `knownPurchaseCost` подписан как известная часть стоимости; при пустом `items` нулевая оценка успешна. Черновики сопровождаются отдельным предупреждением. Цена — последняя неакционная без ограничения давности: UI показывает дату, не гарантирует текущие цены и наличие. Смешивание разных SKU и домашние запасы в расчёт не входят.

400 (включая пустое стандартное Spring-тело), 404, 409 и сеть отображаются как ошибки, а не пустой/бесплатный список. 404 может означать отсутствующий магазин либо ещё не развёрнутый endpoint: UI не утверждает причину без тела ответа. При ошибке обновления сохранённая оценка явно помечена устаревшей. 401 обрабатывается существующим механизмом сессии. Cookie, `cache: no-store`, AbortSignal и отсутствие повторов записи наследуются от общего клиента.

Ключи Query содержат аккаунт, период и точку. Изменение меню инвалидирует и граммы, и все оценки пользователя. После изменения цен в другом клиенте используются ручное обновление, возврат во вкладку и восстановление сети. Push-синхронизации между клиентами нет. Ввод цен/SKU не добавлен: API поиска/списка SKU отсутствует; UI не предлагает фиктивный справочник. Полученные реальные магазины и оценки не пишутся в localStorage/CacheStorage. Демо остаётся отдельным.

Для live-проверки новых endpoint нужен backend, перезапущенный с новым контроллером. Фронтенд не запускает и не изменяет Java. Proxy `/api` на `SMARTMEAL_API_URL` (по умолчанию `http://127.0.0.1:8080`) сохранён.

Проверки: unit-контракт магазинов/оценки/ошибок/инвалидации; браузерные сценарии выбора точки, фильтра сети, неполного покрытия, старой цены, пустого ответа, 400/404/409/401/сети, обновления, изменения периода и ширин 360/390/768/1440. Используются изолированные API-ответы, реальные аккаунты и цены тесты не создают.

## Сравнение магазинов · 20 октября 2026

На живом экране `/shopping` появился режим «Сравнить магазины». Расчёт одной точки сохранён. Поиск городов/сетей общий, в сравнении можно собрать 1–10 уникальных адресов из нескольких поисков и явно нажать «Сравнить выбранные магазины». При изменении состава или применённого периода прежние результаты скрываются до нового запуска. Изменение фильтра поиска само по себе не очищает выбранные адреса.

Контракт: `GET /api/me/shopping-comparison?from=...&to=...&storeIds=501,502` с cookie, без CSRF/записей. Поле ответа — именно `shoppingEstimateResponseList`, каждый элемент соответствует контракту расчёта одной точки. ID берутся из справочника, в клиенте дедуплицируются и приводятся к стабильному порядку для ключа/запроса. Выбор без адресов и свыше 10 блокируется. Период использует общую проверку 1–31 день включительно.

Полные и неполные оценки показаны отдельными группами, с сохранением серверного порядка внутри группы. Минимальная оценка отмечается только среди нескольких полных непустых оценок; при равенстве отмечены все равные. Неполная известная сумма не объявляется минимальной ценой всей закупки. Если полных оценок нет, это прямо обозначено. При пустой потребности нет победителя и расчёта экономии. Денежные/упаковочные расчёты остаются на сервере. «Подробнее» открывает упаковки, непокрытые строки, даты и источники цен выбранного магазина, используя тот же компонент, что и расчёт одной точки.

400/401/404/409/сеть обрабатываются общим клиентом. Ошибка одного магазина не подменяется локальным частичным успехом. При неудачном обновлении ранее полученные результаты явно помечены устаревшими. Ключ Query изолирован по пользователю, периоду и набору ID; AbortSignal отменяет неактуальный GET, результаты прежнего выбора/периода не показываются. После изменения меню инвалидируются также все сравнения аккаунта. Для цен, изменённых другим клиентом, доступны ручное обновление, возврат во вкладку и восстановление сети; push-синхронизации нет. Данные сравнения не пишутся в localStorage/CacheStorage; demo остаётся отдельным.

Проверки сравнения: API-путь и точное поле DTO, cookie/signal, границы выбора, ключи и инвалидация; браузерные сценарии полного/неполного/пустого ответа, равных цен, подробностей, 400/404/409/401/сети, смены периода и состава во время задержанного GET, фильтра сети и ширин 360/390/768/1440. Браузерные тесты используют изолированные ответы и не создают реальных аккаунтов/цен.

## Каталог упаковок и ручные цены · 20 октября 2026

В API-режиме откройте `/shopping?view=catalogue` (также ссылка со страницы `/stores`) либо вкладку «Упаковки и цены». Выберите город/сеть и конкретную точку. Расчёт одной точки и сравнение сохранены отдельными режимами. Поиск упаковок применяется кнопкой, использует буквальное `name`, сбрасывает страницу и выбранную карточку; страницы по 20 элементов. Смена точки размонтирует каталог и формы, отменяет прежние GET; реальные товары и цены не пишутся в localStorage/CacheStorage.

`GET /api/store-products?storeId=...&name=...&page=...&size=20` возвращает `content/page/size/totalElements/totalPages`. Клиент также поддерживает необязательный `productId`. Пустой ответ — отсутствие совпадений/страницы, не ошибка. 400/404/409 отображаются как ошибки, 401 использует общий механизм сессии. Для выбранного SKU отдельно выполняется `GET /api/store-products/{id}/prices/latest`; запросов цены для всех строк нет. Только 404 этого endpoint трактуется как отсутствие цены; если упаковка была удалена, предлагается обновить каталог. Остальные ошибки не маскируются отсутствием цены. После сетевого сбоя ранее полученная цена явно может быть устаревшей.

Карточка показывает сумму за упаковку, дату, источник и акционность. Последняя запись включает акции; оценки закупки и сравнение используют последнюю **неакционную** цену. Это наблюдение, без гарантии текущей цены/наличия.

Форма добавляет `POST /api/store-products/{id}/prices` с `price/observedAt/promotional`, без source. Цена положительная, максимум 10 целых и 2 дробных знака; допускается ввод запятой. Локальные дата/время преобразуются через часовой пояс браузера в ISO UTC, будущее отклоняется, окончательная проверка на сервере. Наблюдение добавляет историю, не меняет прежнюю запись. После 201 показывается подтверждение ответа, последняя цена перечитывается (историческая запись не обязательно последняя), инвалидируются все estimates/comparisons аккаунта.

Если упаковки нет, кнопка «Добавить упаковку» открывает выбор базового продукта через существующие `/api/products?q=...&page=...&size=12[&categoryId=...]` и `/api/product-categories`. Отдельно вводятся название до 300 символов и положительный целый вес упаковки. `POST /api/store-products` передаёт `storeId/productId/name/packageWeightG`; только после 201 выбирается созданный SKU, обновляются каталог/оценки и открывается ввод цены. Создание базового продукта в этой форме не имитируется.

Все POST используют существующий клиент с cookie и свежим CSRF. Во время записи форма заблокирована; синхронный lock предотвращает двойную отправку. Автоматических повторов нет, в том числе после 403/409/сетевой ошибки. При неопределённом сетевом исходе предлагается сначала проверить каталог/последнюю цену, поскольку запись могла сохраниться. Ошибки полей ProblemDetail показаны в форме, локальный успех без подтверждённого ответа не создаётся. Offline-записи отключены. После изменения цен другим клиентом данные обновляются вручную, при возврате во вкладку и восстановлении сети; серверных push-событий нет.

## Съедобная и покупная масса

Поля `shoppingName/edibleYield` сохранены в типах продуктов и снимков; API-каталог базовых продуктов и выбор основы SKU показывают их без подстановки неизвестного коэффициента. Формы создания/редактирования базового продукта в существующем интерфейсе нет, новый редактор не добавлен. Редактор рецепта уточняет: масса сырой съедобной части до приготовления. Список покупок показывает уже рассчитанную backend покупную массу с учётом очистки; клиент не делит её на edibleYield повторно. Калорийность на 100 г относится к сырой съедобной части. Изменение справочника не обновляет существующие снимки меню; новые настройки применятся после удаления и повторного добавления блюда в редактируемое меню. Старые снимки обрабатывает сервер с fallback name/1.
